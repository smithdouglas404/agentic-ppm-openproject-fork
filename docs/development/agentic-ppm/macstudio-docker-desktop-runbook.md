# Mac Studio Docker Desktop runbook

## Scope

This deployment runs the forked OpenProject Agentic PPM product and its supporting services on the user’s Mac Studio Docker Desktop. OpenProject remains the product authority. The retained rich UI is available as a client-facing workspace, while the local agent runtime, memory, graph, ontology, rule, model-routing, and connector services run behind the native OpenProject boundary.

Railway and Manus WebDev are not required runtime dependencies for this deployment. The repository may contain historical deployment evidence mentioning Railway; those records are retained for audit and migration history and are not used by this Compose overlay.

## Required directory layout

Place these repositories as sibling directories on the Mac Studio, or adjust the `agent-runtime` build context in `docker-compose.macstudio.yml`:

```text
agentic-ppm-openproject-fork/
  docker-compose.yml
  docker-compose.macstudio.yml
  .env.macstudio
  modules/agentic_ppm/
  ontology/

governance-agent-server/
  Dockerfile
  agents/
  frontend/
  ontology/
```

The fork’s overlay currently builds the supporting runtime from `../governance-agent-server`. This keeps the fork as the product while reusing the existing rich UI and agent runtime source during the consolidation phase.

## First startup

Copy the template and generate unique local values for every `replace-with-...` entry. Do not commit the resulting file:

```bash
cp .env.macstudio.example .env.macstudio
openssl rand -base64 36
```

Before startup, confirm that `OPENAI_API_KEY` or an approved alternative provider is present if model inference and embeddings are required. A provider key is not generated by Docker; it must be supplied through the local secret file. The key must never be placed in frontend code, Git, logs, or a public Compose file.

Validate the merged Compose configuration without starting services:

```bash
docker compose \
  -f docker-compose.yml \
  -f docker-compose.macstudio.yml \
  --env-file .env.macstudio \
  config --quiet
```

Start the complete stack:

```bash
docker compose \
  -f docker-compose.yml \
  -f docker-compose.macstudio.yml \
  --env-file .env.macstudio \
  up -d --build
```

The first build may take time because the OpenProject and agent-runtime images install Ruby, Node, Python, and frontend dependencies. Do not use `docker compose down -v` during troubleshooting because it removes persistent databases and memory/graph state.

## Verification

Check the container state and health:

```bash
docker compose \
  -f docker-compose.yml \
  -f docker-compose.macstudio.yml \
  --env-file .env.macstudio \
  ps
```

Check service logs by dependency boundary:

```bash
docker compose --env-file .env.macstudio logs --tail=200 backend worker agent-runtime mem0 letta memgraph langflow litellm
```

The initial native verification sequence is:

1. Open the native OpenProject URL and confirm authentication, project creation, Agentic PPM module activation, and the project permission boundary.
2. Create one real sample project and at least one work package, relation, schedule, risk/issue, and membership record.
3. Run the native projection/handoff path and confirm an OpenProject-owned `AgentRun` is created.
4. Confirm the agent runtime receives only the project-scoped evidence envelope through the protected internal network.
5. Confirm the result returns to the OpenProject `AgentRun` with response, evidence references, correlation ID, and explicit approval state.
6. Confirm Memgraph contains source-cited relationships and that graph queries cannot cross the user’s project authorization boundary.
7. Confirm Mem0 and Letta writes/readbacks are scoped to the specialist, tenant, project, and run.
8. Open the retained rich UI and verify that its dashboard, graph, chat, observability, rules, and findings views consume the native OpenProject contracts rather than direct unscoped agent-server data.

A service is not considered operational merely because its container is running. The result must include application-level health, a real project-scoped evidence handoff, and a source-backed response.

## Persistence and backup

Named volumes contain product and service state. Inventory them before any destructive operation:

```bash
docker volume ls | grep -E 'agent|openproject|memgraph|fuseki|langflow|governance'
```

Back up PostgreSQL and MySQL databases using their native clients, and archive graph, ontology, document, and Letta/Mem0 volumes while the services are stopped or placed in a consistent backup mode. Store backups outside the Compose project and test a restore on a separate volume before calling the migration complete.

Never use `docker compose down -v` as a generic fix. It destroys OpenProject, graph, memory, Langflow, and supporting database state.

## Mac Studio compatibility

The stack should run natively on Apple Silicon where images support `linux/arm64`. For images that are only available for `linux/amd64`, Docker Desktop may use emulation; the final handoff must record which services require emulation and measure their startup and runtime behavior. The OpenProject fork’s CI image is not the product runtime and should not be used as the default Mac Studio application image without a corresponding development/runtime Dockerfile.

## Current boundary

The Compose overlay and secret template are committed in the fork and pass merged Compose configuration validation using non-secret test values. The physical Mac Studio is not connected to this session, so no claim is made that its containers are currently running. The next proof must be executed on that Docker Desktop and must validate native OpenProject integration end to end.
