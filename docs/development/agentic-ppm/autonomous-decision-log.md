# Autonomous Decision Log

## Purpose

This log records material decisions made during the delegated autonomous implementation window. Each entry identifies the decision, rationale, boundaries, and the conditions that would require reconsideration. It is part of the delivery evidence for this fork.

| ID | Decision | Rationale | Boundary and review trigger |
| --- | --- | --- | --- |
| AD-001 | The GitHub repository `smithdouglas404/agentic-ppm-openproject-fork` is the upstream-linked OpenProject fork and primary Agentic PPM codebase. | The product must become an OpenProject-native application rather than a separate companion product. | Re-evaluate only if the organization moves the fork to an enterprise GitHub owner. |
| AD-002 | OpenProject remains the operational system of record; Memgraph is the semantic graph runtime. | Project workflows and permissions must remain native, while cross-domain intelligence needs graph-native relationships and provenance. | Validate source-of-truth synchronization and conflict rules before the first real project sync. |
| AD-003 | Letta is the persistent specialist-agent runtime and Mem0 is the scoped memory extraction/retrieval layer. | Separates enduring agent state from portable retrieval memories and keeps both policy-bound. | Re-evaluate after live agent workload and memory-quality measurements. |
| AD-004 | Langflow is the visual composition layer for approved end-user business rules and agent flows. | It enables business-user changes without requiring engineers for every permitted workflow adjustment. | Visual flows cannot bypass OpenProject authorization, credentials, transactional commits, or external write policy. |
| AD-005 | The term AgentKit refers to **Inngest AgentKit**. It is a candidate multi-agent orchestration library, not the primary persistent-agent runtime. | Its agent networks, routers, tools, state, MCP support, and Anthropic support complement event-driven orchestration but overlap with Letta. | Adopt only when a specific multi-agent workflow cannot be expressed cleanly through OpenProject-native services, Letta, and the selected event runtime. |
| AD-006 | Traditional cron is not the primary workflow mechanism for Agentic PPM. | Critical synchronization and agent workflows require idempotency, retries, checkpoints, traceability, and durable event behavior. | Select native Good Job or Inngest after comparative implementation analysis; maintain one authoritative workflow history. |
| AD-007 | No real external credentials, user accounts, or production service activation will be created without an approved target environment and an available authorization path. | The user authorized autonomous decisions but did not supply a target OpenProject instance or secret-management route. | Continue immediately once the extended service environment provides the controlled evaluation instance. |
| AD-008 | The current development sandbox does not provide Docker, so service runtimes are defined through non-blocking Compose profiles and managed-secret adapters rather than started in this environment. | OpenProject, Memgraph, Langflow, and self-hosted Mem0 services require container-capable infrastructure; the user explicitly directed that development not wait for them. | Activate the existing Compose profile in an extended container-capable server environment; do not change the native module contracts. |
| AD-009 | The first code slice is a minimal `modules/agentic_ppm` OpenProject engine with project permissions, native project navigation, protected routes, a transparent capability-state view, and configuration-driven adapters. | This proves the application is being extended in the fork without pretending that unavailable external services are operational. | Add persisted ontology projection metadata and a native event/job implementation next; do not add provider-specific logic to controllers. |
| AD-010 | Feature expansion is frozen until the source-first engineering gates are passed. | The earlier sequence moved from analysis to scaffolding too quickly and did not demonstrate a running OpenProject environment or a real project-to-ontology flow. | Existing scaffolding is unverified; resume only with runtime activation, test-baseline, and proof work described in `source-first-engineering-gate.md`. |
| AD-011 | The Cloud Computer runs the native service in Puma single mode with one minimum and two maximum threads. | The 958 MB VM could cold-boot reliably only after replacing the cluster worker profile; login and authenticated native routes were revalidated after the adjustment. | Re-evaluate when the host is resized or when a production deployment can use a managed runtime with more memory. |
| AD-012 | Native business-rule lifecycle remains authoritative even when a future Langflow editor is enabled. | The project-scoped Business Rules interface uses OpenProject permission checks and the lifecycle service; it explicitly does not fabricate external flow validation. | Permit visual validation only after Langflow is authorized and its result is persisted as governed evidence. |
| AD-013 | Projection jobs mark source records as `projected` and record bounded known-project failures before re-raising. | A controlled failure proved that the job retains phase and error-class provenance without exposing secrets, while success records preserve a completed projection state. | Re-evaluate the payload envelope only when a real external graph sink or retry policy adds a documented requirement. |
| AD-014 | The private-fork module suite uses a lightweight Rails/PostgreSQL workflow rather than rebuilding frontend and browser layers. | The current source branch passed the isolated suite in minutes after the focused workflow removed unrelated image build work. | Keep the full upstream CI path for upstream changes; re-evaluate when module specs require browser assets. |
| AD-015 | Memgraph remains inactive behind a projection governance contract. | The contract specifies managed labels, provenance, health, server-side authorization, and projection-run rollback while the documented Railway endpoint remains unavailable. | Activate only after a valid protected endpoint and health proof are available. |
| AD-016 | Native portfolio intelligence interactions must remain source-backed and deterministic until a live graph and agent runtime are authorized. | The dashboard now filters projected relationships, inspects projected entities, and drills into derived schedule completeness alerts from native work-package fields. This provides useful evidence exploration without inventing graph facts, predictive anomalies, or agent recommendations. | Replace or augment deterministic signals only after graph-query authorization, provenance contracts, and evaluation evidence are demonstrated. |
| AD-017 | PMO and VRO are the only interactive specialists before Letta/Mem0 activation, and their requests must persist as audited unavailable records when the runtime is inactive. | The project-scoped conversation workspace reflects the existing specialist contract, retains request history, and prevents a queued or unavailable request from being presented as a generated response. | Enable live responses only after protected Letta and Mem0 endpoints, scoped identity provisioning, retrieval traces, and end-to-end authorization proof are available. |
| AD-018 | Jira and ServiceNow connection onboarding stores governed metadata rather than external credentials and remains disabled by default. | Model validation now requires a policy-approved HTTPS endpoint, mapping profile, authorization mode, policy version, read-only sync mode, and provenance envelope. The protected form accepts only managed credential references and does not enable the connection. | Re-evaluate once the organization supplies a managed-secret reference and authorized provider endpoint for a read-only health and ingestion proof. |

## Current operating assumption

Implementation proceeds without routine confirmation. The work pauses only for an unavoidable external credential, access boundary, payment, or irreversible production action.
